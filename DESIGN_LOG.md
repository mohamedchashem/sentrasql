# SentraSQL — Design Log
Complete reasoning trail for every planning decision made on this project. This is not a summary — it captures the actual reasoning, including what was proposed, what was pushed back on, what changed as a result, and why. Written and maintained by the human/AI planning side of this project (not by Cline).

---

## 1. How the Project's Scope Was Chosen

### 1.1 Starting point
The initial brief called for a wide list of concepts to demonstrate: LangChain, LangGraph, RAG, NL preprocessing, vector database workflows, prompt engineering, translation, memory, zero-shot/one-shot classification, fine-tuned models, document classification, routing, agent-building, dynamic text-to-SQL/SQL-to-text, and Arabic translation.

### 1.2 Grounding the scope in real evidence
Rather than designing against this abstract list, the decision was made to extract real information about what the target company actually builds, via internal call recordings (Teams recordings with transcripts, in Arabic with English technical terms mixed in — code-switching, not distinct-language translation).

Two internal systems were identified from two separate recordings:

**System A (most recently/actively worked on):** A natural-language querying and automated reporting agent. Core capabilities described: conversational querying ("ask a question, get any information I need"), automated PDF/report generation matching query parameters, time-series aggregation at multiple granularities (monthly breakdowns of daily inflow/outflow, daily breakdowns down to hourly counts), entity tracking (personnel/people counts), site and sub-area/zone filtering, and default timezone handling (defaulting to UTC when Saudi or Egypt timezone isn't specified — this specific detail was flagged as looking like an artifact of a real bug/fallback under pressure, not a deliberate design choice, and this observation directly informed a later decision, see 1.5). The system UI displays active filters alongside answers for transparency/inspection. Infrastructure hint: RTX 4090 (24GB VRAM) mentioned, implying local inference/heavy compute — a real, unavoidable resource gap versus the 4GB VRAM laptop being used for this project.

**System B:** A document classification and routing pipeline. Classifies by full document text content and semantics (explicitly NOT by visual layout/appearance — "مش من شكلها," "بيقرأ التكست كلها"), assigning department/category/access-level labels (HR, Finance, Legal, etc.) using fine-tuned classifiers/embeddings trained on 100+ sample documents. Benchmarked multiple NLP backbones (.NET-based classifiers, FastText, Sentence-Transformer setups) to find the best-performing architecture. Notably, this was a refactor: the engineer (Youssef) inherited a legacy system using hardcoded keyword/string matching and rewrote it to be dynamic and ML/embedding-based.

### 1.3 The RAG/translation gap — a real tension identified and resolved
After reviewing System A, it was noted that the brief's RAG, vector database, and translation requirements had zero evidence in the transcript — System A is purely a structured-data/text-to-SQL problem, with no retrieval-over-unstructured-documents component at all. This was flagged explicitly as a real risk: forcing RAG into the design just to satisfy the brief's checklist, without evidence it reflects real company work, risks looking like exactly the kind of bolted-on, doesn't-actually-fit design that a sharp reviewer would notice — described at the time as the same category of failure as a previously-experienced real gap ("what happens if someone just walks through the camera's frame, not tampering with anything" — a gap that went unnoticed until an external technical lead asked about it in a meeting).

System B was then reviewed and found to also lack any RAG evidence — it's semantic *classification* (text in, one label from a small fixed set out), not retrieval-augmented *question answering* (query in, relevant passages retrieved from a large corpus out). These are different problems even though both involve embeddings, and it was explicitly flagged as an error to blur that distinction ("well they use embeddings, so it's basically RAG-adjacent" was named as an example of inference dressed up as evidence, to be avoided).

**Resolution:** with two systems reviewed and zero evidence of RAG or translation in either, the conclusion was: the company's actual stack is SQL-agent + text-classification-agent; RAG and translation are requirements from the evaluators/brief, not things grounded in the company's actual work. Two options were considered for handling this honestly: (a) don't force RAG into the "mirror their system" narrative, treat it as a deliberately separate, clearly-labeled addition demonstrating brief-required breadth without pretending it reflects observed reality, or (b) treat it as a legitimately plausible but unconfirmed extension (e.g., "a site-analytics company almost certainly has some unstructured content — incident reports, SOPs — that a RAG layer could plausibly serve, even without direct evidence they've built this yet"), explicitly labeled in any write-up as "no direct evidence this exists, but a defensible extension of the same domain."

### 1.4 Decision: build one project, not a combined system, not two projects covering everything
Initially considered building one unified LangGraph system with a router dispatching between a SQL pipeline and a document pipeline (since both were now grounded in real evidence). This was reconsidered: SQL analytics and document classification are two unrelated problem domains with no natural shared entry point — forcing a router between "answer a question about counts" and "classify this HR document" isn't genuine dispatch between related query types, it's artificial coupling of two different apps, which is the same "kitchen sink" smell as trying to cover the whole original concept list in one system.

**Final decision: split into two separate projects** (only the SQL agent — "SentraSQL" — is actually being built in this repo; the document classifier is a separate, later project). Reasoning for why splitting is better than merging: each of the two grounded systems is a complete, coherent problem on its own; forcing them together for "coverage" produces two shallow demos instead of one deep one, and shallow breadth is what weaker candidates default to. This was validated by an external reviewer, who noted the SQL agent specifically is architecturally more interesting (real failure modes: query correctness, guardrails, ambiguous NL resolution) and confirmed the split should be stated explicitly in any write-up as a deliberate decision ("these are two different skill domains — structured query generation vs. semantic retrieval/routing — so I went deep on one rather than shallow on both"), not presented as an omission.

Explicit ground rule adopted from this discussion: if a concept from the original brief list doesn't have a natural home in one of the two grounded systems, the correct response is "then it doesn't need to be its own pillar," not "invent a third pipeline to justify including it."

### 1.5 Domain substitution decision
No access to the company's real database. Two options considered: (1) build synthetic data mimicking their exact domain (site/zone people-counting), (2) use a different domain entirely with the same structural shape.

Option 1 was rejected for two reasons: first, fabricating synthetic data realistic enough to be convincing (correct daily/weekly patterns, not flat random noise) is real, non-trivial effort; second, reproducing their exact domain risked either implying insider access to their literal system, or (per external reviewer feedback, discussed in section 1.6) simply being an unnecessary and slightly presumptuous choice when a public dataset would serve the same architectural purpose without any of that ambiguity.

**Decision: use a real public dataset in an unrelated domain** — UCI's "Online Retail II" e-commerce transaction dataset — chosen because it has the same structural shape needed to demonstrate the same techniques (time-series data, multiple filterable dimensions — product/country — a numeric value column), while being genuinely, non-fabricated messy in the way real production data actually is (missing values, cancellations, adjustment line items), which matters because handling that realistic messiness correctly is itself a demonstrated skill.

### 1.6 External review round 1 — confirmed and one gap found
An external reviewer (a third party asked to sanity-check the plan, not to help build it) confirmed: the scope-narrowing decision (one system) is sound, and the domain substitution is reasonable specifically because fabricating data to resemble a real company's internal system can read as presumptuous, whereas a real public dataset avoids that entirely.

**Gap found:** the original system's timezone-handling requirement (defaulting to UTC for unspecified Saudi/Egypt timezone) has no natural analog in Online Retail II, since that dataset uses naive (non-timezone-aware) timestamps from a single source. Two options were offered: explicitly scope it out and say so, or lightly synthesize timezone complexity via the existing Country column (map country → timezone). **Decision: synthesize it lightly**, reasoning being it's cheap to add and turns a silent gap into a real, visible piece of state the agent has to reason about (which timezone applies to a UK query vs. a UAE query), rather than quietly dropping a feature that was explicitly called out in the source material.

**Confidentiality question raised and resolved:** the reviewer flagged, as a due-diligence point rather than a blocker, whether reproducing this level of specific architectural detail (their exact filter dimensions, their exact timezone-default quirk) from an internal recording was appropriate for an external portfolio piece, contingent on whether the recording was shared specifically as case-study material for this selection process versus general internal access for unrelated reasons. Resolution: the recordings were understood to be usable as reference material for this exact process; text-to-SQL agents are a common, non-proprietary technique regardless, so the underlying approach requires no special clearance. If ever asked directly, the honest answer is: "I listened to a recording, took notes, and used it as inspiration to try to build something in the spirit of what the team is doing" — not a claim of exact replication.

### 1.7 Translation requirement clarified
Initial ambiguity: did "translate to Arabic" mean a literal translation pipeline (queries in one language, forced output in another) or genuine bilingual understand-and-reply capability? Clarified as the latter: the agent should understand and reply in the language the user used, specifically Arabic and English (not open-ended "any language," since that's what's actually evidenced in the source recordings, and a narrower claim is one that can actually be fully tested, versus a broader claim that sounds more impressive but can't be validated as thoroughly).

Two implementation approaches were compared:
- **Option A — rely on the LLM's native multilingual ability** (no explicit translation node; the model reasons and responds in whatever language the query came in). Simpler, fewer failure points, no translation-induced meaning drift, but architecturally invisible — no distinct state transition to show on a live dashboard.
- **Option B — an explicit translate-normalize-respond graph node** (detect language → translate to internal working language, English → process → translate response back). More failure surface, and arguably not the "more correct" engineering choice in isolation, but produces real, visible state (detected_language, normalized_query, localized_answer) suited to the project's stated goal of showing live state transitions, not just correct answers.

**Decision: Option B, for Project A (the SQL agent) specifically**, with the explicit acknowledgment that this choice is justified by demonstrability given the evaluation context (visible orchestration matters here), not by "it's the objectively better way to build this" — a distinction that should be articulable if asked directly. For System B (the document classifier, not built in this repo), the reasoning was inverted: since its primary input is documents to classify rather than conversational queries, and if source documents are in Arabic, the better approach there would be a multilingual embedding model (e.g. LaBSE, multilingual-E5) rather than a translation node — translation isn't necessary if the embedding model already handles the language directly. This was noted as a useful pairing to be able to explain: same underlying "handle Arabic" requirement, two different correct architectural answers depending on whether the surface is conversational or embedding-based.

**Scope decision:** the translation node (Option B) was later deferred out of the v1 build (see section 5.3) in favor of proving the core disclosure-and-guardrail logic first.

## 2. Data Investigation — Full Findings

Investigation was done in three passes, each via a dedicated one-off script (kept in `scripts/`, never deleted, since they are the actual evidence behind every data-policy decision below):

### 2.1 Pass 1 — `scripts/profile_dataset.py` (basic profile)
Dataset: `online_retail_II.csv`, read successfully via UTF-8 (no latin1 fallback needed, despite this dataset commonly requiring latin1 in older references — worth noting the file's actual encoding was cleaner than expected).
- 1,067,371 rows, 8 columns: Invoice (str), StockCode (str), Description (str), Quantity (int64), InvoiceDate (str — NOT a real datetime, flagged for preprocessing), Price (float64), Customer ID (float64), Country (str).
- Date range: 2009-12-01 07:45:00 to 2011-12-09 12:50:00.
- Null counts: Description 4,382 (0.41%), Customer ID 243,007 (22.77%) — all other columns 0 nulls.
- Country: 43 unique values, heavily skewed to United Kingdom (981,330 of 1,067,371 rows).

### 2.2 Pass 2 — `scripts/profile_anomalies.py` (numeric/invoice anomalies)
This pass was run specifically because the basic profile only computed min/max for date columns, leaving Quantity and Price completely unexamined — flagged as a real gap, since this dataset is known to include returns and cancellations that could silently break aggregation queries if undetected.
- Quantity: min -80,995, max 80,995, negative values: 22,950, zero values: 0.
- Price: min -53,594.36, max 38,970.0, negative values: 5, zero values: 6,202.
- Invoice values starting with "C" (cancellation flag): 19,494. Example verified: Invoice C489449, multiple line items, all negative quantity, Country=Australia.
- Top 20 StockCode values by frequency were reviewed to check for visually obvious non-product codes — none of the anomalous codes (see Pass 3) appeared in the top 20, meaning they're individually rare but not necessarily absent or unimportant.

### 2.3 Pass 3 — `scripts/profile_stockcodes.py` (StockCode structural anomalies)
Initial approach: flag every StockCode NOT matching "digits optionally followed by 1-2 letters" as a proxy for "non-product." This returned 63 anomalous codes.

**This approach was explicitly tested, found wrong, and rejected**, not adopted: manual inspection of the 63 flagged codes showed most of them (the `DCGS0058`, `DCGS0076`, etc. series) have genuine product descriptions ("MISO PRETTY GUM," "SUNJAR LED NIGHT LIGHT," "HAYNES CAMPER SHOULDER BAG," "OOH LA LA DOGS COLLAR," etc.) — they are real inventory with non-standard code formats, not administrative noise. Had the regex-based exclusion been applied uncritically, real products would have been silently deleted from the dataset. This was treated as a significant finding in its own right, not just a footnote — a demonstrated instance of catching a plausible-but-wrong approach before it caused damage, worth highlighting rather than hiding in any project write-up.

The actual confirmed non-product codes, identified by manual inspection of descriptions rather than pattern-matching: `POST` (2,122 rows, "POSTAGE"), `DOT` (1,446 rows, "DOTCOM POSTAGE"), `M`/`m` (1,421 + 5 rows, "Manual"), `C2` (282 rows, "CARRIAGE"), `D` (177 rows, "Discount"), `S` (104 rows, "SAMPLES"), `BANK CHARGES` (102 rows), `ADJUST`/`ADJUST2` (67 + 3 rows, adjustment entries attributed to named individuals with dates, e.g. "Adjustment by john on 26/01/2010"), `AMAZONFEE` (43 rows), `gift_0001_10` through `gift_0001_90` (Dotcomgiftshop gift vouchers of varying denominations, low counts each), `CRUK` (16 rows, "CRUK Commission"), `TEST001`/`TEST002` (15 + 2 rows, literal test descriptions: "This is a test product"), `B` (6 rows, "Adjust bad debt"), `GIFT` (1 row), and one stray formatting artifact `"47503J "` (1 row, trailing whitespace on an otherwise real product code — a normalization issue, not a real anomaly).

Also examined: 15 most frequent Description values among Price=0 rows — dominated by missing-description rows (4,382, matching the earlier null count), plus recognizable adjustment/write-off language: "check" (162), "?" (92), "damages" (84), "damaged" (81), "found" (28), "missing" (27), "sold as set on dotcom" (20), "adjustment" (16), and a few real zero-priced product descriptions ("OWL DOORSTOP," "POLYESTER FILLER PAD" variants) suggesting free samples or promotional giveaways.

Also examined and confirmed as a genuine, unreconciled data quirk (not something to "fix"): 3,457 rows have negative Quantity on an invoice that does NOT start with "C" (i.e., a return-like transaction with no formal cancellation flag), and exactly 1 row has Invoice starting with "C" but a positive Quantity (a cancellation-flagged invoice with what looks like a non-cancelled line item). Both directions of this mismatch exist, confirming "cancellation" (C-flag) and "return" (negative quantity) cannot be treated as interchangeable proxies for one another.

## 3. Preprocessing Decisions and Reasoning

Explicit framing adopted: there is a difference between **cleaning** (deleting/altering data because it's inconvenient) and **preprocessing** (normalizing representation so the same real-world thing is always represented identically). The goal was to do the second, and as little of the first as possible.

**Why not switch to a "cleaner" dataset instead of preprocessing this one:** explicitly considered and rejected. Any "clean" alternative dataset would simply hide the same categories of real-world messiness (cancellations, free samples, fee line items mixed with product sales) rather than not have them — synthetic or overly-sanitized alternatives would remove the exact realism that makes correctly handling edge cases a meaningful demonstration. A dataset where every query returns suspiciously round, always-correct numbers was explicitly identified as less convincing than one that visibly handles known messiness correctly.

**Decisions made, each independently justified:**
1. Trim whitespace and normalize case on StockCode — justified by the `"47503J "` and `"m"`/`"M"` findings above; without this, identical products would be double-counted as distinct entities in any grouped query.
2. Tag every row with an explicit `line_item_type` (product/fee/adjustment) field, driven by the hardcoded confirmed list from section 2.3 — not a regex, precisely because the regex approach was tested and shown to misclassify real products.
3. Drop only the two `TEST001`/`TEST002` rows outright — justified as the sole case where the row has zero relationship to real business activity (literal test data), versus every other non-product code which represents a real, if non-product, business event (a postage charge is a real transaction, just not a product sale).
4. Convert InvoiceDate from stored text to a real datetime type — a hard requirement for any time-series aggregation feature to function at all.
5. Explicitly NOT removing: cancellations, negative quantities, zero-price rows, or null Customer IDs. Each was individually justified as representing genuine real-world business conditions (returns happen, samples are given away, guest checkouts exist) rather than defects — imputing or deleting any of these would mean inventing certainty about the data that isn't actually known.

## 4. Query-Time Ambiguity Policy — Full Evolution (v1 → v2 → v3)

### 4.1 Why this policy exists
Identified as the single most important design artifact in the project, following external review feedback: it's not enough to *preserve* quirks in the data (section 3) — a separate problem is how an NL-to-SQL agent *behaves* at query time when asked something that touches those quirks, since that's where a technically-correct-but-misleading answer can silently ship to a user without anyone noticing until much later (explicitly compared to the earlier "walked through frame" gap — the same category of failure, just in a different project).

### 4.2 v1 draft (initial)
Core principle proposed: the agent never silently picks an interpretation of ambiguous data; every assumption gets stated in the answer. Four numbered rules were drafted covering cancellations/negative quantities (included by default = net), zero-price rows (excluded from averages, included in counts), null Customer ID (excluded from customer-grouped queries), and non-product line items (excluded from product-ranking queries) — plus a general rule 5 covering any ambiguity not otherwise addressed.

**Self-identified weakness in v1, flagged before external review:** rule 5's actual enforceability was questioned — it depends on the LLM reliably noticing when it's making an assumption, not just executing a query, and this can't be verified just by writing the rule down; it needs dedicated eval test cases.

### 4.3 External review round 2 — v1 critiqued
Three specific problems were identified:

1. **Rule 1 ("net by default") was found to have a hidden, unaddressed ambiguity.** Net revenue via `SUM(Quantity * Price)` is actually "free" — it requires no explicit cancellation-filtering logic at all, since negative quantities net out automatically via their sign. The real undefined decision was in the *alternative* view: what does "gross-of-cancellations" mean operationally, given the confirmed non-overlap between the C-flag and negative-quantity populations (3,457 / 1 mismatch, section 2.3)? Without pinning this down, "exclude cancellations" is ambiguous between "filter by C-flag" and "filter by negative sign," and these produce different numbers — a gap that would otherwise surface only when someone requested the gross view and got a number that didn't reconcile against a naive reading of the data.

2. **Rules 2 and 4 lacked a composability rule.** A query that triggers both simultaneously (their example: "average price of the top-selling product, excluding postage" — trips both the average-excludes-zero-price rule and the ranking-excludes-non-product rule) had no defined behavior for whether both exclusions get disclosed or just the first one "noticed." Flagged as a real risk that an implementation could pass every single-rule test case while silently dropping disclosures the moment two rules overlap in the same query.

3. **The disclosure counts ("must state how many X were excluded") were identified as being at risk of being narrated rather than computed** — i.e., a real risk that the LLM generates a plausible-sounding number in prose (e.g., "excluding 12 zero-price rows") without that number actually being tied to a real query result. This was elevated from a "policy about behavior" to a required "policy about architecture": the excluded-row count must come from an actual companion query run alongside the main query, and be substituted into the answer via structured data, never generated freeform by the LLM.

A related eval-design point was raised at this stage: a disclosure that is *present but wrong* (e.g., stating "no zero-price rows were excluded" when some were, because the model pattern-matched the sentence template rather than checking a real filter) is a distinct and arguably worse failure mode than a disclosure that's simply *missing* — these need separate eval test cases, not one combined "does it disclose" check.

### 4.4 v2 changes made in response
- Rule 1 pinned down explicitly: "gross-of-cancellations" defined specifically as excluding invoices where Invoice starts with "C." "Returns" defined as a wholly separate, independently named filter: `Quantity < 0`, unrelated to the cancellation flag. These are two different named filters a user can request, not one ambiguous toggle.
- Composability rule added explicitly: when multiple rules apply to one query, all applicable exclusions are disclosed, not just one.
- The disclosure-sourcing constraint was written into the policy as an explicit architectural requirement, not just a behavioral expectation: excluded-row counts must be computed by a paired/companion query and passed as structured data into the answer step, with the LLM only responsible for phrasing.

### 4.5 External review round 3 — v2 critiqued further
Two more issues surfaced:

1. **The "net revenue is free" claim needed a footnote.** While the *formula* (`SUM(Quantity * Price)`) is correct as a definition of net revenue, the word "net" could misleadingly imply that cancellations are being cleanly matched and offset against a corresponding original sale. The 3,457 unflagged negative-quantity rows are direct evidence that some of that netting has no visible matching prior sale in the same invoice — meaning "net" here means "sum the signed values exactly as recorded," not "verified reconciliation of returns against sales." This distinction needed to be stated explicitly so nobody downstream (including future-self) assumes more rigor than actually exists in the number.

2. **The eval set's disclosure-count-accuracy category needed a third variant, not two.** The existing plan checked "correctly says zero" and "doesn't hallucinate a nonzero number when it should say zero" — but a third case was identified as necessary: a case where the correct excluded count is a specific, hand-verified nonzero number (e.g., manually pre-counting that exactly N postage/fee rows should be excluded from a specific top-seller query), checking that the agent's *stated number matches exactly*, not merely that it's nonzero. This was explicitly identified as catching a different failure mode than the first two categories — a companion query that is syntactically wired up and executing, but subtly wrong (e.g., an off-by-one from a join issue, or an incorrectly scoped WHERE clause) — which "is it zero or not" checks cannot catch.

3. **An architecture-level open question was raised and explicitly deferred to the graph-design stage rather than resolved within the policy doc itself:** given that companion queries now need to be generated alongside a main query without drifting apart from it, is that one LLM call producing both together as structured output, or two separate sequential node invocations? This was flagged as no longer a policy-doc-level question — it had become an agent-architecture dependency the policy had created, needing its own explicit resolution (see section 5).

### 4.6 v3 — final policy (as filed; see full text also embedded in this project's `graph/state.py` docstrings and `graph/nodes.py` docstrings for the corresponding implementation contract)

Core principle: the agent never silently picks an interpretation of ambiguous data, and never states a fact about the data (especially an exclusion count) that wasn't actually computed by a query.

1. Revenue/quantity totals default to net (`SUM(Quantity * Price)`, signed values summed as recorded — explicitly not implying verified reconciliation between returns and sales, given the confirmed C-flag/negative-quantity mismatch). Gross-of-cancellations = named filter `Invoice NOT LIKE 'C%'`. Returns = separate named filter `Quantity < 0`. Agent states which was applied.
2. Averages exclude Price = 0 by default; excluded count sourced from a companion query, never composed in prose.
3. Customer-grouped queries exclude null Customer ID by default; same sourcing constraint.
4. Product-ranking queries exclude fee/adjustment/voucher-tagged rows by default; same sourcing constraint.
5. Composability: multiple applicable rules are all disclosed, not just one.
6. Architectural constraint: the LLM produces structured query intent, not raw SQL for either main or companion queries; a deterministic code layer compiles both from that shared structured intent, guaranteeing they cannot drift apart; the LLM only composes final phrasing from already-computed values.
7. General fallback: undocumented ambiguity (e.g. vague time phrases like "last month") is stated explicitly, never guessed silently.

## 5. Architecture Decision Trail — Full Reasoning

### 5.1 Resolving the "one LLM call vs. two" question (from section 4.5)
Neither of the two options originally posed was adopted. The LLM's role was instead narrowed to producing structured query intent only (aggregation type, target metric, filters, grouping, time range) — never SQL text for either the main or companion query. A deterministic code layer then generates *both* the main SQL and any companion count queries by filling shared templates from that one structured intent object.

Reasoning: since both queries are built by code from one shared source of truth, they cannot drift apart from each other structurally — there is no scenario where the main query's WHERE clause differs from a companion query's WHERE clause, because neither is independently-authored free text. This was explicitly framed as matching DeepSeek's actual strengths/weaknesses as the chosen model: ask the LLM to do the one thing it's reliably good at (extracting structured meaning from natural language), and ask deterministic code to do the one thing it's reliably good at (generating exact, repeatable SQL with zero drift) — rather than asking a weaker/cheaper model to reliably author two independent, consistent pieces of SQL text.

This also changes what the SQL guardrail validates: deterministically-generated SQL against a known, bounded template set, rather than arbitrary free-text SQL the LLM could have written any way it wanted — assessed as a meaningfully stronger safety position.

### 5.2 Full 8-node graph design and external review round 4
Initial 8-node sequence proposed (numbered 2 through 7, plus 6.5, reflecting that "Node 1" conceptually was the deferred language-normalization step): extract_query_intent (LLM) → detect_applicable_rules (deterministic) → compile_sql (deterministic) → validate_guardrails (deterministic, AST-based) → execute_queries → assemble_disclosures (deterministic) → assemble_answer (LLM, constrained) → memory/checkpointer update.

**External review found three real gaps:**

1. **No field existed anywhere in the state to carry rule 5's "general fallback" disclosures.** Rules 1–4 are mechanically detectable by a deterministic node checking structured fields in query_intent — but rule 5 covers genuinely interpretive ambiguity (e.g., resolving "last month" to a concrete date range) that only the LLM-based intent-extraction node could ever notice, since it's inherently not an enumerable, fixed rule set the way rules 1–4 are. Without a dedicated field, rule 5 would exist in the policy document but have no mechanism in the graph ever responsible for triggering it.
   **Fix:** an `assumptions` field added to the query_intent structure, populated by the intent-extraction node whenever it resolves genuine ambiguity, read later by the answer-assembly node alongside the rule-based disclosures.

2. **The (deferred, but designed-for) PDF export branch was identified as a potential disclosure-policy bypass.** If a PDF-generation node were to independently format raw results into a document without going through the same disclosure-assembly logic as the chat-answer node, it would create a second output surface that could present numbers without the required exclusion caveats — and a report is exactly the kind of artifact a user might trust *more* than a chat answer, precisely because it looks official, making this a worse version of the same failure rather than a lesser one.
   **Fix, and decision on how to implement it:** the PDF node (when eventually built) must not touch raw companion-query results directly; it must consume the chat-answer node's already-assembled disclosure text and lay that out in the PDF, rather than re-deriving disclosures independently (a "shared function both nodes call" alternative was considered and explicitly rejected in favor of direct reuse of already-generated text, on the reasoning that reuse structurally eliminates the possibility of drift, whereas a shared function only reduces the *likelihood* of two implementations diverging over time).

3. **No defined behavior existed for a companion query failing while the main query succeeds.** Flagged as a case where, left unspecified, the default behavior that would likely fall out of unguided implementation is "answer anyway, silently skip the disclosure" — assessed as the worst possible outcome, since it produces an answer that looks fully policy-compliant while silently missing a required caveat.
   **Fix:** made explicit as a hard-stop rule — if a rule fired (per applicable_rules) and its companion query fails for any reason, that is a hard stop; the graph routes to an error path and never emits an otherwise-disclosure-required answer with a missing disclosure.

### 5.3 V1 scope-cut decision (what gets built first)
Proposed cut: defer language normalization and PDF generation from the first working build, prove the core intent→rule→compile→guardrail→execute→answer loop first.

**External review pushed this further:** memory/checkpointer (multi-turn conversational state, e.g. "now break that down by hour" as a follow-up) was also moved into the deferred pile, not kept in v1 core. Reasoning: conversational state and anaphora resolution is a genuinely separate technical capability from the disclosure-and-guardrail architecture that is the actual thesis of this project, and there was a real, named risk of burning significant debugging time on checkpointer-specific state bugs that would not actually advance or demonstrate the thing the project exists to prove. The explicit sequencing guidance given: if time remains after the core 6-node loop works end-to-end, add memory, then language normalization, then PDF export, roughly in order of "how much does this add to the core argument versus how much additional surface area/risk does it add."

**Final v1 scope:** extract_query_intent → detect_applicable_rules → compile_sql → validate_guardrails → execute_queries → assemble_disclosures → assemble_answer, single-turn only, English only, no memory, no PDF. Everything else is a named, explicitly sequenced future addition, not an implicit "maybe if there's time."

### 5.4 Schema-consistency review (round 5) and two further fixes

1. **Assumptions field mandatory-vs-optional risk.** Making the `assumptions` field required (a fix from 5.2) was noted to actually *increase* a specific risk rather than only closing the original gap: a model instructed to always populate a field is more likely to manufacture plausible-sounding content for it than one instructed to populate it only when relevant. This is the same underlying principle already applied to disclosure counts ("present but wrong is worse than absent") but was initially missed as applying identically to this new field. Resolved by explicitly stating, in both the schema and the eval plan, that an empty `assumptions` list is a normal, fully valid, expected result — and adding a dedicated eval case (a query with no genuine ambiguity, checking the list comes back empty rather than invented) as the necessary mirror to the "assumption correctly fires" case.

2. **Companion-query-failure hard-stop needed its own eval case, not just a graph edge.** The behavior was specified precisely in the graph design (5.2, point 3) but nothing in the eval plan actually exercised it — flagged as exactly the kind of thing that is correctly built once and then silently regresses after a later, unrelated change, if nothing is actively testing for it. Added as its own eval category: simulate a companion query failure and confirm the graph actually takes the error branch rather than the answer-assembly node quietly proceeding on main_results alone.

3. **The `Assumption` data shape was decided to be structured, not free text** — a `{field, raw_phrase, resolution}` triple rather than a single prose sentence — specifically because free-text assumptions would force the eval harness into fragile fuzzy string-matching against expected wording, undermining the credibility of the eval set itself. Structured fields let a test check "did the system correctly flag `time_range` as ambiguous" independent of the exact phrasing used, and also give the answer-assembly node a consistent template to phrase from rather than reformatting arbitrary prose.

4. **`CompanionQuery`'s shape was found not to fit rule 1 at all**, in a later pass: `CompanionQuery` was defined around "the excluded-row count," which fits rules 2, 3, and 4 (all "N rows were excluded" style disclosures) — but rule 1's disclosure is not a count at all, it's a statement of *which filter was applied* (net / gross / returns), and as established in 4.6, net revenue requires no companion query in the first place. This meant the original plan implicitly assumed all four rules fed one uniform pipeline, which rule 1 structurally cannot do.
   **Fix:** a third, distinct disclosure source was named explicitly — "direct-filter-based" — alongside "assumption-based" and "companion-query-based." A unifying `Disclosure` shape (source: rule / assumption / direct_filter; label; detail) was introduced specifically so a dedicated, separate deterministic node (not folded into the answer-assembly node, to keep deterministic transformation logic independently testable from the one remaining LLM call in the pipeline) could convert all three sources into one consistent shape before the answer-assembly node ever sees them — meaning that node only ever has to reason about one interface, not three special cases.

## 6. Standing Principles Established Through This Process
(Worth restating on their own, since they recurred multiple times across unrelated decisions above)

- **A field that "must always be populated" creates real pressure on a model to manufacture plausible-but-false content for it.** This applies to disclosure counts and to the assumptions list alike, and should be checked against any future mandatory structured field added to this system.
- **A disclosure or claim that is present but wrong is a worse failure than one that is simply missing**, because it looks trustworthy while being false. Eval design throughout this project treats these as two separate failure categories, never one combined "did it disclose correctly" check.
- **Deterministic logic and LLM-driven logic should live in separate graph nodes wherever possible**, even when it would be technically simpler to combine them into one step, specifically so a bug in one is distinguishable from a bug in the other, and so the deterministic piece can be unit-tested independently of any LLM call.
- **When two outputs must never structurally disagree with each other** (e.g., a main query and its companion verification query), the safest architecture makes them both derive from one shared, code-generated source of truth, rather than trusting two independently-authored generations (by the same or different LLM calls) to stay consistent with each other.
- **A regex or pattern-based heuristic that "looks like it should work" needs to be tested against real examples before being trusted**, not adopted on the strength of its apparent logic alone — the StockCode classification approach is the concrete example of this principle in action within this project.

## 11. Country-to-Timezone Mapping Methodology (new decision, supporting §1.6)

**Decision:** each of the dataset's real countries is mapped to exactly one IANA timezone name (e.g. "Europe/London"), not a fixed numeric UTC offset. Reasoning: IANA names delegate DST correctness to standard datetime tooling automatically, whereas a fixed offset would require manually maintained seasonal adjustment logic for DST-observing countries for no real benefit.

**Known simplification:** for countries whose real territory spans multiple timezones (in this dataset, practically only the USA), one representative/most-common business timezone is used rather than modeling sub-national regions — the dataset has no state/region field that would let us resolve this correctly, so attempting finer granularity would mean inventing precision the data doesn't support.

**Ambiguous/non-country Country values found in the actual dataset, and their explicit handling:** `Channel Islands`, `European Community`, `Unspecified`, and `West Indies` are not resolvable to a single real country or timezone. These are explicitly mapped to UTC — deliberately reusing the same UTC-default fallback behavior observed in the original company system (DESIGN_LOG §1.2), rather than inventing a new convention for genuinely ambiguous cases.


**Correction to §11, found during implementation:** the original plan to use "the first entry of `pytz.country_timezones`" as each country's representative timezone was based on an incorrect assumption that this list is ordered by population/business relevance. In practice it follows `pytz`'s internal `zone.tab` file ordering, which is not population-based — this produced incorrect results for Australia (`Australia/Lord_Howe` instead of Sydney), Canada (`America/St_Johns` instead of Toronto), and Brazil (`America/Noronha` instead of São Paulo). Fixed with an explicit override dictionary for these 3 known multi-zone countries in the dataset, checked before falling through to pytz's default; all other resolved countries were verified correct as-is since their pytz-first-entry happened to already be their primary city.


## 12. Guardrail Row-Limit Disclosure (extends §4's disclosure policy)

**Decision:** when a query result is truncated by the SQL guardrail's row-limit enforcement, this is treated as a fifth disclosure case, using the same `Disclosure` mechanism already built for the four query-ambiguity policy rules (§4) — not a separate, ad hoc behavior. Rationale: a truncated result silently returned as if complete is the same class of failure as an undisclosed exclusion count. Resolution: a `result_truncated` flag is set on truncation and normalized into a `Disclosure` object.

**Composability:** if both the main query and one or more companion queries are truncated on the same turn, this follows the same composability rule as the four policy rules (§4, rule 5) — all applicable truncations are disclosed together, not just one. A single answer may therefore state multiple distinct truncation facts if more than one query was affected.

**Row-limit ceilings — status: provisional, not finalized.** Two tiers are planned, but neither number is derived from real requirements yet:
- A low ceiling for any query result feeding into Node 7 (LLM phrasing). Every query type in the current policy (§4) resolves to a scalar or a small group-by (at most a few dozen rows) — no expected query type should routinely approach even a few hundred rows. The ceiling being set (500) is explicitly a pathological-case safety guard against an unanticipated high-cardinality group-by, not a number expected to be hit in normal operation. This should be revisited once real query patterns are observed.
- A separate, higher ceiling reserved for a future bulk-data consumer (PDF/report export), which is explicitly deferred and not yet scoped (see §5.3, v1 scope cut). Any number set now (currently 50,000) is a placeholder — the correct value depends entirely on what that node ends up needing (e.g., "revenue by day for a year" needs ~365 rows; "every transaction in a date range" on a busy range could need far more), and should not be treated as settled until the report node is actually designed.


## 13. QueryIntent Schema Corrections (found while designing detect_applicable_rules)

**Constrain `metric` to a `Literal` enum**, not a free-form `str`. Every rule-trigger condition in `detect_applicable_rules` depends on exact string equality against `metric` (`"revenue"`, `"quantity"`, `"unit_price"`). An unconstrained string field means a Node 2 output like `"total_revenue"` instead of `"revenue"` would silently fail to trigger the correct rule, with no error anywhere — exactly the "wrong silently" failure mode this project has been built to avoid. Fixed by constraining `metric` to the exact canonical values `compile_sql` and `detect_applicable_rules` already depend on.

**Add distinct-count representation.** The schema had no way to express `COUNT(DISTINCT customer_id)` — "how many unique customers bought X" — as opposed to `COUNT(*)`. This is a genuine missing capability, not just a missing rule trigger; `compile_sql` will also need this once such queries are supported. Added a `distinct: bool` field to `QueryIntent`, defaulting to `False`, so `aggregation="count"` + `metric="customer_id"` + `distinct=True` represents a unique-customer-count query.

**Rule 2 (`AVG_EXCLUDE_ZERO_PRICE`) trigger extended from `unit_price` only to any price-derived metric — `unit_price` or `revenue`.** Revenue is `quantity * unit_price`, so a zero-price row also produces zero revenue for that transaction, distorting a revenue average the same way it distorts a price average. `quantity` is explicitly excluded from this extension — a zero-price row still has a real, non-zero quantity (e.g. a free sample), so quantity averages aren't distorted by zero-price rows and don't need this rule.


## 14. Truncation Disclosure Composability (closes open item from §12)

**Decision:** main-query truncation and companion-query truncation are independent disclosure sources, following the same composability pattern already established for the four policy rules (§4, rule 5) — all applicable truncations are disclosed together, not merged into one statement or only the first noticed. Node 6.5 treats "was the main query truncated?" and "was companion query X truncated?" as additional boolean-gated disclosure sources, structurally alongside the four rule-based sources and any assumptions — not a special combined case requiring separate logic.

**Schema homes, decided concretely:** `GraphState.main_truncated: bool` for the main query (a `CompanionQuery` field doesn't fit, since the main query isn't a `CompanionQuery`); `CompanionQuery.truncated: bool` for each companion, alongside its existing `status`/`excluded_count` fields — same kind of per-query metadata, same object.


## 15. Entity-Ambiguity Scope Limitation (extract_query_intent)

**Decision:** the entity/product-name ambiguity trigger in `extract_query_intent` only catches zero-match cases — a product/entity reference that doesn't map to any exact known value in the schema, routed as a hard validation failure (same pattern as `compile_sql`'s `no_matching_data` gate). It does NOT catch multi-match cases — e.g., a query referencing "the mug" when the real catalog contains several mug-related products — since true disambiguation would require a retrieval/fuzzy-matching step against the live product catalog to give the model visibility into real candidate values, which doesn't exist in this system.

**Why not build it:** considered and explicitly deferred, not overlooked. A retrieval-backed disambiguation feature (Option A) was scoped as a genuinely new subsystem — its own search mechanism, new failure modes, new eval coverage — comparable in effort to a full additional guardrail rule, given the project's timeline. Choosing not to build it is a deliberate scope decision under time constraints, not an unrecognized gap: the alternative (Option B, adopted) hard-fails cleanly and asks the user to be more specific, rather than fabricating a disambiguation judgment ungrounded in real data — the latter would have been a worse failure mode than the capability gap itself, since a confident-but-wrong assumption is worse than an honest "I don't know."

**Status:** named post-v1 item if time allows; not committed to for this project.

## 16. DeepSeek Strict Function-Calling — Live-Verified Behavior and Resulting Schema Corrections

**Context:** before implementing `extract_query_intent`, DeepSeek's strict function-calling mode was probed live (real API calls, not assumed from documentation) to verify three things the node's design depended on: enum enforcement, null/empty-list consistency, and general schema constraint support. Findings materially changed the design.

**Finding 1 — `enum` constraints are advisory (prompt-level influence), NOT enforced server-side.** Live-verified: a value explicitly excluded from a field's declared `enum` was returned by the API with HTTP 200 and no error, when the model was persuaded to violate it. Strict mode guarantees well-formed JSON with all required keys present — it does not validate that individual values respect `enum`, type, or any other value-level constraint declared in the schema.

**Consequence:** Pydantic validation of the parsed tool-call response is not a redundant backup check — it is the only real enforcement layer for every value-level constraint this system cares about (canonical metric names, country/line_item_type values, etc.). This must be treated as load-bearing, always run, and any failure treated as a real extraction failure, not a warning.

**`enum` is still used in generated tool schemas** despite being unenforced, since it measurably improves compliance (a real, verified prompt-steering effect) — but this must be stated explicitly wherever the schema is defined and in this design doc, not left implicit: *"enum constraints here are advisory prompt-steering only, not enforcement — do not add a new optional field and assume enum protects it without also checking the Pydantic model enforces it."*

**Finding 2 — nullable union types are rejected by the API at request time (HTTP 400), not just discouraged.** `["array", "null"]`-style nullable typing cannot be expressed in a DeepSeek strict-mode tool schema at all. **This supersedes an earlier decision** (that `group_by = null` was an acceptable, unambiguous representation of "no grouping requested") — that representation is no longer possible under any circumstance. This constraint is schema-wide, not limited to `group_by` — it applies to every optional field in `QueryIntent` regardless of type.

**New, uniform convention adopted for every optional field in `QueryIntent`:**
- **List/dict-shaped fields** → empty list/dict when absent. Live-verified reliable (12/12 correct) when the tool description explicitly states the convention ("use `[]`, never `null`, never omit, when there is nothing to include — an empty list is a normal, valid result").
- **Optional scalar fields** (a single date boundary, a single filter value) → wrapped in a small object carrying an explicit, per-field `present: bool` flag alongside the value. A sentinel value (e.g. empty string meaning "not provided") was explicitly rejected as the convention, since it risks colliding with a legitimate real value that happens to look like the sentinel — the same category of ambiguity this project has avoided elsewhere (e.g. the near-miss filter-value handling in `compile_sql`).
- **Granularity is per-field, not per-filter-group.** E.g. a date range filter has independent `start_present`/`start` and `end_present`/`end` pairs, not one flag governing the whole object — this is required to represent real, common partial-range phrasing like "since March" (start present, end absent) or "before December" (end present, start absent).

**This restructures `QueryIntent.filters`** from a loosely dict-like shape into explicit typed sub-objects per filter kind, each using the per-field `present` convention above.

**Downstream propagation, named explicitly as a required follow-up, not assumed to be automatic:** `compile_sql`'s WHERE-clause construction and `detect_applicable_rules`'s trigger conditions were both designed and reviewed several rounds prior, against `filters` as a loosely dict-like structure. Both must be revisited once this restructuring lands — any code currently checking dict key existence must instead check the corresponding `.present` flag before reading a value. This is a propagation of an already-made decision, not a new design choice, but is recorded here explicitly so it isn't missed when those nodes are revisited, since their filter-handling details should not be assumed fresh at that point.

**New failure mode from the `present`/value pattern, requiring both a prompt instruction and a dedicated validation check:**
- Prompt instruction: "when a `*_present` flag is false, leave its paired value field at its type default — do not populate it anyway."
- Post-parse validation: detect and hard-fail on either inconsistent state — `present: true` with an empty/default value, or `present: false` with a populated value. This is a distinct failure shape from the list/null coercion problem and requires its own explicit check, not coverage assumed from existing normalization logic.
- **Both directions are treated as hard failures in v1, for uniformity — but they carry asymmetric real risk, worth recording:** `present: false` with a populated value is the dangerous direction — silently normalizing it away (trusting the flag, discarding the value) risks quietly dropping something the model may have extracted correctly while only mislabeling the flag, an error that would never surface. `present: true` with an empty value is comparatively low-stakes, since both "trust the flag" and "trust the value" resolve to the same practical outcome (nothing usable either way). If this is ever relaxed later for performance/UX reasons, the low-risk direction is the one that could safely be softened to auto-normalize instead of hard-failing — the dangerous direction should not be.
- **Eval case to include:** a targeted test for `start_present: false` with a populated `start` value, confirming it correctly hard-fails rather than silently discarding or silently trusting the value — more precise than a generic malformed-response case, since it exercises the specific dangerous asymmetry this finding exists to prevent.

**Finding 3 — the `assumptions` field's emptiness is entirely instruction-driven, with a measured effect size.** Live-verified: with an explicit "empty list is a normal, valid result" instruction in the prompt, 12/12 calls returned a clean empty list on unambiguous inputs. Without that instruction (a neutral prompt, same inputs), the model fabricated assumption entries in 5/6 calls. This confirms, with real measurement, the hallucination-pressure risk already anticipated when the `assumptions` field was made required (see earlier entry on required-but-emptyable fields) — and establishes that the mitigating instruction is not optional polish, it is load-bearing and must be prominent, not buried in a longer description.

**Post-parse normalization/coercion step, confirmed necessary despite fields no longer being nominally nullable:** because strict mode does not actually enforce declared types on output values (Finding 1), nothing structurally prevents the model from emitting `null` for a field declared as array type despite the schema disallowing it. The coercion step is a real backstop against confirmed non-enforcement, not defensive code against a hypothetical.

**Retry policy — the retry attempt reuses the exact same call configuration as the first attempt**, including `"thinking": {"type": "disabled"}` when required for the model in use (see operational note below) — not a fresh or differently-configured call. Retry occurrence is recorded via `state.intent_extraction_retried: bool`, kept visible/inspectable rather than silently smoothed over.

**Operational note, confirmed live:** for `deepseek-v4-pro` (and any model where thinking mode defaults on), `"thinking": {"type": "disabled"}` must be explicitly sent whenever `tool_choice="required"` is used, or the call fails with HTTP 400 ("Thinking mode does not support this tool_choice"). This is a required, tested configuration detail for this node's implementation, not something to be rediscovered later as a mysterious failure.
